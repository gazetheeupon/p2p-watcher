    How this works: this device (the "host") indexes the files in memory and connects directly to viewers' browsers over a WebRTC data channel. Video is streamed in range-requested chunks straight from this device's disk — nothing is ever uploaded to a server, and there's nothing to sign up for. The connection is set up through free public WebSocket trackers, but the actual offer/answer signaling is AES-GCM encrypted first, so the tracker only ever sees an encrypted blob, not what you're sharing.
    
    
    Viewers are permanently read-only. A connected viewer can watch and can never write, delete, or modify anything on this device — that's enforced by this device rejecting any write-type message outright, not just hidden by the viewer's UI.
    
    
    Keys never leave your control. The encryption key for a shared folder lives only in the viewer link's URL fragment (after the #, which browsers never send to a server) and in this browser's own localStorage. Closing this tab stops the stream; reopening it and re-dropping the same folder is required to share it again.
    
    
    .mkv / .avi files are remuxed on this device the first time a viewer requests them, using an in-browser build of FFmpeg — that can take a little while for a large file (a status line above will say so), and only happens once per file per session.
    
  
    

  
    
    
    Troubleshooting
    
    
    
      A viewer says they're stuck on "Connecting…"
      
    Check the count next to your folder above. If it already shows someone watching, the WebRTC connection itself is fine and they're most likely waiting on a first-time .mkv/.avi remux — ask them to wait, the status line on their side should be showing progress. If it still shows nobody connected after a minute or so, the two networks likely can't reach each other directly (some restrictive routers/firewalls block peer-to-peer connections entirely, and there's no relay fallback if that happens) — try a different network.
    
    
    
    
    
      Why does a .mkv or .avi file take a moment the first time?
      
    Browsers can't play those containers directly, so this device remuxes (or, when needed, re-encodes) the file into a browser-playable format on the fly the first time it's requested. That's what the "Remuxing…" status above means; the result is cached in memory for the rest of this session, so the same file plays instantly for the next viewer.
    
    
    
    
    
      Is this OK to use for movies or shows I've downloaded?
      
    This tool only moves bytes between devices you control (or that you personally chose to share a link with) — it doesn't index, host, or distribute anything itself. Whether it's OK to share a particular file is the same question it would be for any personal file-sharing tool: only share files you actually have the right to share.
