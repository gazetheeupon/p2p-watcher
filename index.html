    How this works: the PC you drop a folder onto (the "host") indexes the files in memory and connects directly to other browsers ("clients") over a WebRTC data channel. Video is streamed in range-requested chunks straight from the host's disk — nothing is ever uploaded to a server, and there's nothing to sign up for. The connection is set up through free public WebSocket trackers, but the actual offer/answer signaling is AES-GCM encrypted first, so the tracker only ever sees an encrypted blob, not what you're sharing.
    
    
    Clients are permanently read-only. A connected device can watch and can never write, delete, or modify anything on the host's computer — that's enforced by the host rejecting any write-type message outright, not just hidden by the UI.
    
    
    Keys never leave your control. The encryption key for a shared folder lives only in the share link's URL fragment (after the #, which browsers never send to a server) and in this browser's own localStorage. Closing the host's tab stops the stream; reopening it and re-dropping the same folder is required to seed again.
    
  
    

  
    
    
    Troubleshooting
    
    
    
      Nothing happens after I open a share link
      
    The host's browser tab has to stay open and on this page for as long as you want to stream — closing it (or the host's computer sleeping) stops seeding. If the host is on a different network than the client, some restrictive routers/firewalls block the peer-to-peer connection entirely; there's no relay fallback if that happens.
    
    
    
    
    
      Playback stalls or won't start on a large file
      
    Everything streams over a single WebRTC data channel at whatever speed the host's upload connection and the path between the two devices allows — a large 4K file over a slow upload will buffer slowly. .mkv/.avi files are also remuxed on the host on first request (see below), which takes a moment before the first byte can be sent.
    
    
    
    
    
      Why does my .mkv or .avi file take a moment to start playing?
      
    Browsers can't play those containers directly, so the host remuxes (or, when needed, re-encodes) the file into a browser-playable format on the fly using an in-browser build of FFmpeg, the first time it's requested. That one-time step is what the "Remuxing…" status means; the result is cached in memory for the rest of that session.
    
    
    
    
    
      Is this OK to use for movies or shows I've downloaded?
      
    This tool only moves bytes between devices you control (or that you personally chose to share a link with) — it doesn't index, host, or distribute anything itself. Whether it's OK to share a particular file is the same question it would be for any personal file-sharing tool: only share files you actually have the right to share.
